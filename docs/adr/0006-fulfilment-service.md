# 6. The fulfilment service

Status: accepted

## Context
A bought kit has to become devices: an identity, a one-time claim token for the buyer, a password for the controller, and a record in Pulse. Orderflow stays generic (ADR 1) and knows nothing of what a kit contains, and Pulse only registers what it is told. The contract already names the owner: fulfilment consumes `order.confirmed.v1` and `order.shipped.v1` and publishes `device.allocated.v1`. A printed QR code is not part of this work.

## Decision
- `Greenhaus.Fulfilment` is a separate ASP.NET Core service with its own PostgreSQL database (`fulfilment` schema, migrations on startup), the outbox relay and inbox consumer pattern of ADR 3 (copied, with a note, rather than shared), and its own queue `fulfilment.events` with a dead-letter queue.
- **Allocation.** For every unit of a kit SKU on a confirmed order it allocates a device: an id `ghx-` plus 12 random hex characters, a claim token and a broker password of 32 random bytes each, URL safe. What a kit contains comes from `data/kit-capabilities.json`; other products on the order are ignored. It is idempotent per order, SKU and position, so a redelivered message, or the same order confirmed twice, never allocates a second device.
- **What travels.** `device.allocated.v1` carries the SHA-256 hex of the claim token (the contract format), a salted hash of the broker password and the kit's capabilities. The token and the password never leave the service in an event.
- **Credential hash format.** `pbkdf2_sha256$<iterations>$<salt base64>$<hash base64>`, PBKDF2 with SHA-256, 100000 iterations, a 16 byte salt. The contract calls the hash opaque to Pulse, which stores it for the broker to verify. This is the format this service writes. The MQTT bridge of Pulse decides what the broker verifies, and if it needs another format only `Allocator.CredentialHash` changes.
- **Packing bundle.** `GET /api/fulfilment/v1/orders/{orderId}/allocations` (contract `contracts/openapi/fulfilment-api.yaml`) shows, for a device in the packing room, the claim token, the claim link (`{Web:BaseUrl}/claim?d=..&t=..`, what a QR would hold) and the password to flash. It needs the realm role `fulfilment-admin`; development mode gives it to everyone unless an `X-Roles` header says otherwise. The role is not in the development realm yet, so a Keycloak run needs it assigned by hand.
- **Shipping.** `order.shipped.v1` moves the order's devices to `ship_requested`. A worker apart from the consumer tells Pulse (`POST /devices/{id}/ship`), so a slow or missing Pulse never holds up the queue. Pulse registers a device when it consumes `device.allocated.v1`, which can be after the shipment, so a 404 is retried like an outage: a wait of 5 seconds that doubles up to 5 minutes, and after 8 attempts the device is shown as `pulse_failed`. A refusal that will not change (for example 409) fails at once. `POST .../allocations/retry` puts failed devices back in the queue. When Pulse accepts, the plaintext token and password are erased: they are shown once, at packing.
- **Return or refund before shipping.** The devices are retired in Pulse (`POST /devices/{id}/retire`, same worker) and their secrets erased. After shipping they are left alone: the buyer has the goods, and what happens to returned goods is Orderflow's concern.
- Authentication is Keycloak JWT with the development mode of the other services. OpenTelemetry counters cover allocated, shipped, retired, retried and failed devices and the outbox and inbox.

## Consequences
- Greenhaus is the owner of "what is in the box", so Orderflow needs nothing but its order events, and Pulse nothing but `device.allocated.v1` and the ship and retire calls it already has.
- Pulse registers a device from `device.allocated.v1` when its events are switched on (`Events__Enabled`, its `docker-compose.events.yml`). Without that, a shipped order ends `pulse_failed` and the service shows it instead of hiding it. The Greenhaus API already remembers which order a device was sold in, so `device.claimed.v1` carries it.
- Checked live against Pulse `main` with its Keycloak and RabbitMQ: allocation, registration in Pulse (state `allocated`, all channels, actuators and the heater's thermal cutoff), shipping (`shipped`), a claim in Pulse with the token from the packing bundle (so the token hash format is the one Pulse verifies), and retirement of a device whose order was returned before shipping.
- The secrets sit in the database while a device is in the packing room, which is the price of showing them to the person who flashes the controller. They are sealed (see the addendum), and the window is short: they are erased when Pulse accepts the shipment.
- Tests run against a real PostgreSQL and RabbitMQ with a fake Pulse and a fake clock, and check the HTTP responses and the published events against their contracts. A separate test pins the wire format of the Pulse calls.
## Addendum: packing secrets are sealed at rest
- **What is sealed.** The claim token and the broker password of a device in the packing room are encrypted with AES-GCM before they reach PostgreSQL, with a random 12 byte nonce per value. The stored form is `enc1:` and base64 of nonce, tag and ciphertext. The allocation id, the device id and the column name are the associated data, so a sealed value that is copied to another row, or the password sealed into the token column, fails to open. A changed value fails too.
- **The key.** `Fulfilment:SecretsKey`, base64 of 32 bytes. Outside the development auth mode the service does not start without a valid key. In development without a key a random key is made up for the run and a warning says that sealed secrets then do not survive a restart. `docker-compose.yml` passes `FULFILMENT_SECRETS_KEY` with a development default that is published in the repository, so local runs keep working across restarts and a real run must set its own key. Rotating the key is not built: a device in the packing room under an old key would need to be re-sealed, and the window is short.
- **What a bad value does.** The packing bundle answers `500` with the code `secrets_unreadable` (documented in the contract). It never sends the sealed text, never the secret, and never a guess. The device stays allocated, and the original value opens again once it is put back.
- **Rows from before.** An earlier version stored the secrets in the clear. At start-up, after the migrations, every row whose secret is not sealed is sealed once, and the service logs how many. It is idempotent, so after the first start of this version nothing readable is left, and a value in the clear is never accepted as a sealed one when reading.
- **What it does not do.** It protects the database and its backups, not the running service or the person who reads the bundle: the bundle is plaintext on purpose, to the packing room only.
