# 11. The automation loop

Status: accepted

## Context
Greenhaus is a controller, not only a monitor (D11): a pump waters when the soil is dry, a lamp lights a dark pot, a fan cools a hot one. Pulse stays generic and only carries commands to devices, so the policy of when to run what lives on the Greenhaus side (N6), within safety limits that hold for every tier (spec 4a). Until now the mode of an actuator was stored and nothing acted on it.

## Decision
- **The rules are pure code** in `Greenhaus.Domain` (`AutomationRules.Decide`): from the pot's requirement for the actuator's metric, the latest readings, the actuator's safety limits and what it remembers (last run, run time today, runs in a row that changed nothing) it returns one decision: run for N seconds, stop, suggest, block, or nothing. Every decision names a stable code and the actor of the audit log (`automation`, or `safety` for a guard).
- **What each actuator reacts to:** the pump to soil moisture below the minimum, the heater to temperature below the minimum, the lamp to light below the minimum, the humidifier to air humidity below the minimum, the fan to temperature above the maximum (D17) and airflow below the minimum. The worst zone decides and zones are never averaged. The requirement's margin is the hysteresis: a running actuator is stopped once the metric is back above the minimum plus the margin (or below the maximum minus it).
- **Safety is not a feature of a tier.** Whatever the tier: a run is at most the actuator's own maximum (and a sensible default per kind), runs are spaced by the minimum interval counted from the end of the last run, the daily cap is respected (the last run is shortened to fit), a reading older than 15 minutes means nothing is done, the pump needs a calibrated sensor, a heater needs a declared hardware thermal cutoff, and the kill switch stops everything. After N runs in a row (default 3, or the user's `maxFruitlessRuns`) that did not move the metric by a threshold, the actuator is **blocked**, the person is told, and nothing runs until they act (a run by hand or a new mode clears it): an empty tank or a broken pump is not watered forever.
- **Modes.** `Off` does nothing. `Notify only` never sends a command: it suggests once per episode (the episode ends when the pot is back in range) through a notification and an audit entry. `Auto` runs. A freshly claimed actuator starts in notify-only (spec 4a).
- **The loop** is a hosted service in the API (`Automation:Interval`, default 30 s, `Automation:Enabled`), `AutomationRunner` + `AutomationCycle`. Each pot is handled in its own transaction under a PostgreSQL advisory lock, so several API instances never decide for the same pot at once. A failing pot is logged and retried in the next round. Commands go through `ICommandSender` (Pulse), and a Pulse failure counts nothing and is retried next cycle. Everything the loop does is in the audit log with the Pulse command id, and `command.completed.v1` fills in the outcome as for manual runs. A lasting condition (a silent sensor, a used-up daily cap) is written down once, not every cycle.
- **State** the loop needs lives on the actuator (columns, one migration): the persisted state (idle or blocked), the block reason, last run and its length, `RunningUntil`, run seconds today (UTC day), runs in a row without effect and the reading the last run started from. The actuator state shown to the app is derived: blocked (kill switch or safety stop), running, or idle.
- **Downgrade (D25).** When the effective tier drops, every actuator whose mode is above what the new tier allows for its metric falls back to notify-only (`TierClamp`), with an audit entry, safety unchanged and nothing deleted. It runs right after an `entitlement.changed.v1` is applied, and in every control cycle for an entitlement that simply lapsed (it has a `validUntil`). The plan-change notification carries what was lowered (`lowered`) so there is one message, not two; for a lapse without an event the loop sends the plan-change notification itself, once. Pots beyond the new pot limit stay as they are (the contract has no read-only flag yet): the limit only stops new pots.
- **Notifications** use the closed set of kinds of ADR 10 (`automation_suggestion`, `actuator_blocked`, `plan_changed`) with structured params, no text.

## Consequences
- The three tiers' automation promise is real: soil moisture and light run automatically on the free tier within the caps, and the rest is notify-only until a higher tier.
- The loop is decided by what Pulse reports. Until Pulse offers commands, `pulse_not_supported` is logged each cycle for a dry pot with an actuator on auto and nothing runs; a kit emulator that executes commands completes the closed loop.
- Not done yet: the tank. Pulse reports the water tank as a safety channel that Greenhaus does not link to a pot, so "tank empty" is an input of the rules that is never true here; the fruitless-run protection covers an empty tank indirectly. Schedules and time windows and multi-condition rules (higher tiers in the spec) are not part of this step.
- Two instances cannot double-decide, but a command sent just before a failed save can be sent again in the next cycle; the controller's own hard limits and the minimum interval are the guard.
