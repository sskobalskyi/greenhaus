# 5. The billing service

Status: accepted

## Context
Billing owns paid subscriptions and, later, grants earned by purchases, so that Orderflow stays independent of Greenhaus (ADR 1). Until now it only existed as a part of the mock. The contract is `contracts/openapi/billing-api.yaml`, and the Greenhaus API already asks billing's tier questions through events (ADR 3).

## Decision
- `Greenhaus.Billing` is a separate ASP.NET Core service with its own PostgreSQL database (`billing` schema, migrations on startup) and its own container. It shares only the pure rules with the rest of the repository, in `Greenhaus.Domain`: prices, the grant thresholds and how the effective entitlement is computed.
- It implements the whole contract: plans (public), subscribe and cancel with a demo payment token, subscription lifecycle, invoices and grants (read only). The demo provider declines a token ending in `-declined` (402, kept as a failed invoice). A token ending in `-renewal-fails` is accepted now and fails at the next renewal, which makes the subscription `past_due`.
- Time is a `TimeProvider`, and a period and a grace period are configuration (`Billing:Period`, `Billing:Grace`), the compressed demo clock of the contract. The same `BillingProcessor` brings state up to the clock: it runs for one user whenever they call the API, so an answer is never stale, and for everyone on a timer (`BillingTicker`). Tests move a fake clock and ask.
- Authentication is Keycloak JWT with the same development mode as the API. Everything is scoped to the token's subject. CORS allows the dev web origins, with no credentials.
- Tests run against a real PostgreSQL and check every response against the OpenAPI document. The contract walk fails if an operation is not exercised.

- **Purchase grants** come only from order events (the API lists them, it never creates them). `order.confirmed.v1` in US dollars earns a grant by the thresholds in `Billing:Grants` (default $30 for 3 months of Gardener, $80 for 12, $150 for 6 months of Druid; placeholders of the spec). A grant is unique per order id, and a grant of a tier the user already holds starts when the running one ends, so they extend and never stack. `order.returned.v1` and `order.refunded.v1` put the grant of that order at risk for the grace period (7 days). The background job then revokes it, and an active grant is revoked when it expires. A refund of an order that was never returned has the same effect, because it cancels the order. A refund of any amount counts: partial refunds are not told apart. Orders in another currency earn nothing until there is a rate. `order.return_cancelled.v1` (a return that was registered but not completed was cancelled) brings a grant that the **return** put at risk back to active: its end date is the one it had, the deadline is cleared, `grant.status_changed.v1` (active) is published and, when the effective tier rises again because of it, `entitlement.changed.v1` with reason `grant_started`. The grant remembers why it is at risk (`AtRiskReason`, `returned` or `refunded`): a refund cannot be undone, so a grant at risk because of a refund, or refunded after its return, is never restored. A grant whose grace period is over is not restored either: the job revokes it on its next run (or already did), and a revoked grant stays revoked. A grant that was at risk before the column existed has no reason and is not restored. An event for an order without a grant, for a grant that is not at risk, or a repeat does nothing.
- **The effective entitlement** is the best tier among the active subscription and the grants that count (an at-risk grant counts until its grace ends), computed by one pure function in `Greenhaus.Domain`. Billing keeps what it last announced for each user and publishes `entitlement.changed.v1` only when the tier, the end or the health of the source changed, with the previous tier. The reason names where the tier comes from, because the Greenhaus API labels the source from it. The end (`validUntil`) is also what makes the API drop the tier on time even if an event is late.
- **Events** go out through an outbox written in the same transaction as the change (subscription and grant changes, the entitlement state), relayed with publisher confirms to `integration.events` with the contract headers: `subscription.changed.v1`, `grant.status_changed.v1` and `entitlement.changed.v1`. Order events are consumed from the durable queue `billing.events` through an inbox keyed by message id, with one retry and then the dead-letter queue `billing.events.dead`. Tests validate the published payloads and headers against the AsyncAPI document. The messaging code is a copy of the Greenhaus API's with billing's names, because a shared project would only save a few files and tie the two services together.
- **Identity:** order events carry the Orderflow customer id (a Keycloak subject of Orderflow's realm), and billing uses it as the user id of the grant. That only matches the Greenhaus user when both apps sign people in through the same realm, which is the ecosystem plan's goal but not true of the local setup yet: until then a purchase grants a tier to a user id that nobody signs in with. A mapping (or the shared realm) is a later step.

## Consequences
- The web app can use the real billing by pointing `VITE_BILLING_BASE` at `http://localhost:8092/api/billing/v1`.
- Subscribing replaces the single subscription row of a user, so history lives in the invoices.
- Renewal catches up periods one by one, so a long absence produces one invoice per period.

## Dunning
A payment that fails does not leave a subscription `past_due` for ever.
- When a renewal fails the subscription becomes `past_due` (`subscription.changed.v1` with that status), the period is still extended so access goes on, and a dunning clock starts at the failed payment (`PastDueSince`).
- While `past_due`, billing tries the stored payment method again every `Billing:RetryInterval` (default one day). Each failed attempt is a failed invoice, so the history shows every attempt. The first retry that works records a paid invoice, returns the subscription to `active` and announces it, with no cancel and no change of tier.
- When `Billing:DunningPeriod` (default seven days) has passed without a payment the background job cancels the subscription: `subscription.changed.v1` with status `cancelled`, and the effective tier is computed again from what is left. With no purchase grant the tier falls to Novice and `entitlement.changed.v1` has reason `cancelled`; with a grant the tier is the grant's and the reason is `grant_started`, because the Greenhaus API labels the source of a tier from the reason. Nothing is deleted, and the person can subscribe again, which starts a fresh subscription without the old dunning clock.
- A person can mend a `past_due` subscription before it ends by subscribing to the same plan again with another payment method token: that replaces the payment method, pays at once and clears the dunning clock. (An `active` subscription on the same plan is still refused with `already_subscribed`.)
- The job and the API run the same code, so a request sees the state of the clock, and running the job twice does nothing the second time. A `past_due` row from before dunning existed gets its clock on the first run.
- The demo provider's tokens: `...-renewal-fails` is refused at every renewal and every retry, `...-renewal-recovers` is refused at the first renewal and accepted when billing retries, anything else is accepted.
- Cancelling twice is harmless, and a subscription cancelled while `past_due` ends at its period end like any other.
- Not done: a notice to the person before the cancel (the Greenhaus API already notifies a lowered plan from `entitlement.changed.v1`), and a different retry schedule than a fixed interval.
